> Ideas discutidas el 2026-06-11. **No son tareas listas**: cada una necesita su `superpowers:brainstorming` antes de planear. Se guardan aquí con el análisis honesto (incl. lo que NO resuelven) para no re-derivarlo.

### 5.1 — Structured outputs para fiabilizar el parsing JSON del router

**Idea original:** reemplazar `wizParseJson()` (repli regex frágil, [buddy/www/index.html:5602](../../../buddy/www/index.html)) por structured outputs / JSON schema.

**Matiz importante (la premisa "los 3 lo soportan igual" es falsa):** cada proveedor tiene mecanismo distinto, NO un `response_format` compartido:
- **OpenAI** — `response_format:{type:'json_schema', strict:true}` → schema estricto real (gpt-4o-mini OK).
- **DeepSeek / Qwen / Groq** — solo `response_format:{type:'json_object'}` (JSON mode: garantiza JSON sintácticamente válido, **no** conformidad al schema). Suele exigir la palabra "json" en el prompt (el wizard ya la tiene).
- **Gemini** — campo distinto: `responseMimeType:'application/json'` (+ `responseSchema` formato OpenAPI).

**Dónde tocar:** parámetro **opt-in** (`json:true` / `jsonSchema`) en `chatCompletion()` ([index.html:4558](../../../buddy/www/index.html)) → threadeado a `callTextProvider()` ([index.html:4511](../../../buddy/www/index.html)), que traduce por proveedor en el `if(type===…)` existente. NO activar JSON global (la mayoría de las 8 tareas devuelven texto plano: resumen mémoire, bridge).

**Efecto palanca (mejor argumento):** `extractFollowUpsAndBridge`, `extractAndUpdateGoals`, `generateChapters`, perfiles → también parsean JSON de `chatCompletion()`. Un `json:true` en el router los fiabiliza a TODOS, no solo el wizard. Pasa de parche local a mejora transversal.

**Lo que NO resuelve:** el límite 900 chars del campo `prompt` (no expresable útil en schema → seguir con `slice(0,900)`); un schema estricto sobre un markdown libre no aporta más que "es string".

**Caveats:** mantener `wizParseJson` como red de seguridad (con JSON mode `JSON.parse` casi siempre éxito → el repli regex queda casi muerto pero inofensivo); el objetivo real es matar el **repli degradado** (`{name,description,prompt:raw}`, ~`5647`) que fabrica personas falsos en silencio. Probar DeepSeek-R1 (`deepseek-reasoner`) + JSON mode en dispositivo (caprichoso, puede devolver content vacío).

### 5.2 — Repensar la mémoire (contexto largo + embeddings locales)

**Idea original:** menos capas de extracción LLM (cada una = punto de alucinación), más inyección de transcripts recientes + retrieval por embeddings locales (transformers.js en la WebView).

**Tensión clave que la formulación oculta:** la contrainte real de Zova NO es "raw vs extracción", es **la voz tiempo real**. Las capas de extracción existen para **comprimir** (de ahí `slice(0,900)`, `MEMORIES_IN_PROMPT=4`): OpenAI Realtime / Gemini Live facturan caro al token y son sensibles a latencia. El prompt caching ayuda al prefijo estable, pero el modelo de voz procesa todos los tokens audio+texto cada turno y el soporte de caching varía. → **Inyectar transcripts brutos reintroduce el coste que las capas eliminaban.** Conclusión: siempre habrá una etapa de budget/compresión en voz; el contexto largo no la borra. Es un **híbrido**, no un reemplazo.

**Dónde tiene razón:** 7 capas post-session = 7 llamadas LLM = coste+latencia+7 puntos de alucinación → reducible. Embeddings >> bag-of-words actual ([`selectRelevantMemories` index.html:7723](../../../buddy/www/index.html), overlap de palabras ≥4 letras contra el *prompt del persona*, **sin query viva** porque el retrieval ocurre 1 vez al abrir sesión). transformers.js local = **victoria privacy** (embedding on-device, 0 API) → alineado con Bloque 5.

**Lo que embeddings NO reemplazan** (son estado/generación, no retrieval): Objetivos+progresión (`buddy_goals_*`), Follow-ups (engagements), Bridge proactivo (generativo), y la commande "souviens-toi que…" (memoria de oro, dictada por user, 0 alucinación). → No se puede colapsar todo; se reemplaza el *ranking* y se reducen los *resúmenes*, no el estado.

**Coûts cachés transformers.js en WebView móvil:** download one-time del modelo (~20-30 MB quantisé, p.ej. `all-MiniLM-L6-v2`/`bge-small`), cold start WASM, RAM extra sobre la app 11k líneas, batería. **Migración de almacenamiento:** vectores (float arrays) no caben en localStorage → IndexedDB → todo el trabajo privacy (`wipeAllAiData`, borrado granular, export) debe re-cubrir el nuevo store.

**Reco (validar antes de apostar la archi):** NO rehacer la mémoire de un bloque. **Primer paso aislado y medible:** reemplazar el scoring de `selectRelevantMemories` (keyword → embeddings locales) con una **query real** (`recentTranscriptContext` o el último turno, no el prompt persona). Esto: prueba la viabilidad de transformers.js-en-WebView **en el Xiaomi** (cold start/RAM/batería) antes de comprometer la archi; 0 impacto en el budget voz (retrieval sigue acotado a 4); mantiene las capas de estado intactas; gain de pertinencia inmediato. Si rinde, *después* atacar la reducción de capas de resumen.
